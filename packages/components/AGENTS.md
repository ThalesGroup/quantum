# packages/components/ — `@quantum-ds/components`, specifications and vanilla CSS reference implementation

The components package: `specs/` holds the technology-agnostic specifications
(`packages/components/specs/AGENTS.md`) and `src/` the reference implementation of every
component in plain CSS and HTML. The web implementation is what the site renders, and an example
of an implementation a web team can follow. The package publishes and exports **only the
specifications**: `pnpm components:build` (`scripts/build-components.mjs`, also run by `pnpm build`
and the package's `prepack`) copies them to `dist/` (not committed), which `files` and `exports` of
`package.json` publish (`@quantum-ds/components/components/<id>.spec.json`, `foundations/…`,
`schema/…`, `a11y/…`, `platforms.json`). Never edit `dist/`; never export `src/`: it stays in the repository, and the docs site (`apps/docs/`) imports it by relative path,
never through the package name. The tokens it reads come from `@quantum-ds/tokens`
(`packages/tokens/`).

```
specs/                                   component.schema.json + one spec per component, foundations, a11y registry, platforms.json -> specs/AGENTS.md
src/index.css                            entry point: fonts -> foundation CSS -> component CSS (the token CSS is not imported here, see below)
src/fonts.css                            webfonts named by the font-family tokens (Google Fonts)
src/foundations/<id>.css                 hand-written global CSS of a foundation (code.css: marked lines), semantic tokens only
src/components/<id>/<id>.css             hand-written component styles
src/components/<id>/<id>.template.mjs    pure render(props) -> HTML string
src/lib/template-utils.mjs               escaping helpers + icon ligatures (Material Symbols)
```

The generated token CSS (`packages/tokens/dist/css/raw.css`, `semantic.css`,
`components/<id>.css`, generated by `scripts/build-tokens.mjs`, never edited) and the generated
syntax highlighting theme (`packages/tokens/dist/shiki-theme.json`) live in the tokens package.
`src/index.css` does not import the token files: a page loads the tokens entry point
`@quantum-ds/tokens/css/index.css` (raw, semantic, then one file per component, in cascade
order) first, then `src/index.css`.

## CSS rules

- Root class `.ds-<id>` on the element named in the spec's `implementations.web.element`.
- Read **only** `--<id>-*` custom properties (generated from the component tokens) and private
  `--_*` properties. No literals, no semantic or raw variables. The validator errors on
  unknown `--<id>-*` names and warns on literals.
- Pattern: declare private properties (`--_background`, `--_color`, …) once on the root with
  the default option and state values, then let option and state selectors *only*
  reassign private properties. Layout and typography declarations appear once.
- Enum properties: `[data-<prop>="<option>"]`. The default option may be implicit
  (`:where([data-emphasis="accent"], :not([data-emphasis]))`).
- Several color axes (Button: emphasis × intent): one rule per combination sets a ladder of
  private properties (`--_background-default`, `--_background-hover`, …), wrapped in `:where()`
  so all combinations share one specificity; the state rules then only pick the rung
  (`--_background: var(--_background-hover)`). This avoids one rule per combination × state.
- States: write native pseudo-class **and** forced attribute together, and guard against
  disabled: `:where(:hover, [data-state="hover"]):not(:disabled, [data-state="disabled"])`.
  Order rules default → hover → active → disabled so the cascade resolves conflicts.
- Focus: `:focus { outline: none }` plus `:is(:focus-visible, [data-state="focus-visible"])`
  drawing the ring from the component's outline tokens. Never `:where()` here: the ring rule
  must match the reset's specificity and come after it, or the reset hides the ring.
- Respect `prefers-reduced-motion`: any `transition` or `animation` needs a
  `@media (prefers-reduced-motion: reduce)` override (validated).
- Parts: `.ds-<id>__<part>` with `data-part="<part>"` on the element.
- The component's Figma blueprint (`packages/figma/src/blueprints/<id>.mjs`) is its layer tree
  in Figma and in Penpot (`@quantum-ds/penpot`), read from this CSS and the template: a new part, a changed layout or a new token slot
  changes it in the same change (`packages/figma/AGENTS.md`; `pnpm impact` lists it).

## Color modes

The component CSS never mentions modes. `packages/tokens/dist/css/semantic.css` declares the
default (light) values on `:root, [data-theme]` and the other modes in `[data-theme="<mode>"]`
rules; the generated component token files are declared on `:root, [data-theme]` too, so every
alias resolves again inside each context. A consumer picks the mode with the attribute:

```html
<html data-theme="auto">                  <!-- follows prefers-color-scheme -->
  <section data-theme="dark">…</section>   <!-- this region is dark whatever the page mode -->
</html>
```

`light`, `dark` and `auto` are the values today (`packages/tokens/tokens.config.json` → `modes`,
`css.modes`). No attribute means the default mode. Each context also sets `color-scheme`, so
native controls and scrollbars follow. A component that needs a color per mode gets it from a
semantic token of the mode overlay, never from a `[data-theme]` selector in its CSS.

## Fonts

`src/fonts.css` loads, from Google Fonts, every family the font-family tokens name (Inter,
Fragment Mono, and the Material Symbols Outlined icon font at the axis values of the
`font.icon.*` tokens), and `src/index.css` imports it first. Without it the browser falls back to the
generic family and nothing renders as designed. When a family token changes, change the URL
in the same commit: the validator errors on a primary family that `fonts.css` does not load.
The component CSS never names a font; it only reads typography tokens.

## Platform scope

The web implementation is the reference rendering and the only one in this repository. It
covers every state and example that includes the web (no `platforms`, or `platforms` listing
`web`); the validator skips the others and the site lists them without rendering. A state or
example that exists only on another platform never needs CSS or template code.

## Form controls with a wrapper root

- A control whose label, description and error message are parts (Checkbox, Radio group, Switch,
  Text field, Textarea, Select, Progress bar) has a wrapper root (`div`, `fieldset`) and a native
  control inside it, named by `implementations.web.rolePart`. The root carries the enum options
  (`data-size`) and the forced `data-state`; the native element carries the native attributes
  (`disabled`, `required`, `readonly`, `checked`, `aria-invalid`, `aria-describedby`).
- The label is a `<label for>` pointing at the control's id (the template takes an `id` prop and
  numbers instances without one); descriptions and error messages are referenced by
  `aria-describedby`. Never `aria-label` when a visible label exists.
- States are written twice: the native pseudo-class or attribute on the control
  (`:checked`, `:disabled`, `[aria-invalid="true"]`, `[readonly]`), and the forced state on the root
  (`.ds-x:where([data-state="checked"]) .ds-x__control`). Rules follow the spec's state order and
  guard hover against the states that win over it (`:hover:not(:checked, :disabled)`), so the CSS
  resolves a combination the way the token rule does (`packages/tokens/AGENTS.md` "Which token applies").
- The native control is drawn by the component (`appearance: none`); marks, dots and thumbs are
  pseudo-elements sized as fractions of the control's size token, in `currentColor` from a color
  token, never a literal length. A repeated part (Radio group options) also takes `data-state` per
  instance, which the states matrix forces through the entry's `state`.
- The `attrs` prop adds attributes to the native control (`name`, `autocomplete`, `data-*`): it is
  how the docs site wires its own forms with the components.

## Composite components and popups

- A component built on another (Dropdown on Button) renders that part with the other
  component's template and its `attrs` prop (extra attributes, a `class` appended to its root
  class), never a copy of its markup. Its CSS styles only its own parts; the other component's
  CSS styles the rest.
- A popup that opens from a control uses the native popover API (`popovertarget`, `popover`,
  `popovertargetaction="hide"` on the actions inside), placed with CSS anchor positioning with
  the trigger as its implicit anchor, inside `@supports (position-area: …)` so browsers without it
  keep the default popover placement. No script: the browser handles Escape, outside clicks,
  focus order and focus return.
- The forced state that shows the popup (`[data-state="expanded"]` on the root) displays it in
  the flow for review, without the top layer.
- Popover ids must be unique in the page: the template takes an `id` prop and numbers
  instances in render order without one.
- Instance enum properties of a repeated part (a menu item's intent) are `data-<property>`
  attributes on each instance; an entry's sandbox-only `state` forces that instance's state.

## Template rules

- `export function render(props = {})` returning a string; `export const meta = { id, selector, icons? }`.
- Props are the spec property ids (camelCase) plus the sandbox-only `state`.
- Escape every interpolated value with `escapeHtml`/`escapeAttr`.
- Never touch `document`; the module runs in Node (build) and in the browser (playground).
- Icons: `renderIcon(name)` from `src/lib/template-utils.mjs` writes the ligature name of a
  Material Symbols glyph (the icon font, `icon.*` tokens). Any valid name renders; `ICONS` is
  the list the playground offers, extend it there. The icon part styles the glyph from its
  component's `<id>.icon.*` tokens (family, weight, fill, grade, optical size, size).
- Accessibility (validated, see `agents/accessibility.md`): render the native element that carries the
  role (`packages/components/specs/a11y/roles.json` → `web.elements`) and no redundant `role`; map booleans to native
  attributes (`disabled`); put `aria-hidden="true"` on every part marked `decorative`; never
  render a control without an accessible name.

## Adding a component

`pnpm new:component <id> --name "Name" --role <role>` creates the files (and a starter Figma
blueprint, `packages/figma/AGENTS.md`), builds the tokens (which regenerates the tokens entry
point `packages/tokens/dist/css/index.css` with the component's token file) and only then adds
the one `@import` line of the component's CSS to `src/index.css`, so a running dev server never
imports a generated file that does not exist yet. Keep the import order: `fonts.css`, then the
foundation files, then the component files.

The docs site is built with these components (`apps/docs/AGENTS.md` "Built with the design
system"): once the component's `implementations.web` is final, `pnpm validate` lists every
native control of the site it covers (same element, same ARIA role). Switch those controls to
the component's template in the same piece of work.

## Syntax highlighting

The syntax highlighting theme lives in the tokens package: `packages/tokens/dist/shiki-theme.json`,
exposed as `@quantum-ds/tokens/shiki-theme.json`, is a theme named `quantum` for
[Shiki](https://shiki.style) (TextMate / VS Code theme format) generated by `pnpm tokens:build`
from the code tokens (Code foundation). Its colors are
`var(--global-text-code-*)`, `var(--global-text-on-base-neutral-primary)` and
`var(--global-bg-level-1-default)`: one theme
for every mode, following `data-theme` like the components, as long as the page loads the token
CSS. Pass the JSON object to Shiki (`themes: [theme]`, then `theme: theme.name`), or to any tool
built on it (Astro `markdown.shikiConfig.theme`, VitePress). Import it from the package
(`import theme from '@quantum-ds/tokens/shiki-theme.json' with { type: 'json' }`). Its scopes are
written for CSS, HTML, JavaScript, JSON, shell, YAML, diff and Markdown.

A theme cannot paint whole lines. `src/foundations/code.css` (imported by `src/index.css` before the
component styles) draws the lines marked by Shiki's notation transformers
(`@shikijs/transformers`: `transformerNotationHighlight`, `transformerNotationDiff`,
`transformerNotationErrorLevel`, default class names `highlighted`, `diff add`, `diff remove`,
`highlighted error`, `highlighted warning`): a background from `global.bg.code.*` and a marker
that does not rest on color (a bar, `+`, `-`, `×`, `!`, with alternative text). Foundation CSS
reads semantic tokens only, never component tokens, and holds no literal color.
